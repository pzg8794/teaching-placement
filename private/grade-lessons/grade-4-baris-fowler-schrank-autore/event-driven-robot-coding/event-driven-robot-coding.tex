\section*{UDL and Inclusion Supports}
\subsection*{Multiple Representation}
\begin{itemize}[leftmargin=*]
\item Demonstrate the event with a visible physical trigger before showing the block code.
\item Keep trigger and response language paired on a chart: when this happens, do this.
\item Use one predictable test area for all students first.
\end{itemize}

\subsection*{Multiple Action / Expression}
\begin{itemize}[leftmargin=*]
\item Allow students to predict orally, with arrows, or in block form before launch.
\item Use pair roles such as flashlight/controller and coder.
\item Provide a debug checklist with three questions: trigger, code, environment.
\end{itemize}

\subsection*{Multiple Engagement}
\begin{itemize}[leftmargin=*]
\item Use immediate robot response as motivation for repeated testing.
\item Frame unexpected behavior as a clue rather than failure.
\item Keep challenges short enough for several iteration cycles.
\end{itemize}

\section*{Teacher Moves / Script / Routines}
\begin{itemize}[leftmargin=*]
\item Physically demonstrate the event before naming the block.
\item Ask students to predict first, then launch.
\item Stop to compare one working event stack and one non-working stack.
\item Close by having students name the trigger and the robot response.
\end{itemize}

\section*{Common Errors and Debugging}
\begin{itemize}[leftmargin=*]
\item Students may confuse repeated motion with event-driven behavior.
\item Sensor placement or lighting conditions can cause inconsistent results.
\item Students may change too many things at once while debugging.
\end{itemize}

\section*{Extensions and Simplifications}
\begin{itemize}[leftmargin=*]
\item Extension: compare two different event triggers for the same robot response.
\item Simplification: use one event and one response only.
\item Extension: add a condition or loop after the event logic works.
\end{itemize}
